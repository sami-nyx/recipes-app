# recipes-api enhancement plan

Non-functional upgrade plan for `recipes-backend/recipes-api`: robustness, scalability, security, and restructuring. Nothing here changes the API's request/response behavior unless explicitly called out — this is groundwork for later behavior changes, not a rewrite.

Status legend: `[ ]` not started · `[~]` in progress · `[x]` done

## 4. Restructuring (splitting files)

The app is small enough that this hasn't hurt yet, but the shape is already visible.

- [x] **`config.py`** — env-var loading and config assembly pulled out of `app.py`'s inline `configure_app()`/`get_required_env()` into its own module. Same required env vars, same validation order, same error text, same config values — purely a file move.
- [x] **`extensions.py`** — `db`/`bcrypt`/`jwt` singleton instances moved out of `models/user.py` (and `app.py` for `jwt`) into one dedicated extensions module, imported wherever they're needed. Avoids `models/` owning app-wide singletons.
- [x] **Validation/schema layer** — validation was hand-rolled and inconsistent (thorough in `update_user`, nearly absent in recipe create/update). Added `validation/` (`common.py`: generic `require_string`/`optional_string`/`optional_number`/`optional_string_list` helpers; `recipes.py`: `validate_recipe_payload()`), called once at the top of `RecipeController.create_recipe`/`update_recipe` before any DB work. Hand-rolled rather than marshmallow/pydantic — no such dependency exists yet, and this closes the actual gap (recipe input wasn't checked at all) without bundling in a new dependency. This *is* the behavior change flagged below: previously-accepted malformed input (missing title, nameless ingredients, non-numeric servings, `"parts": null`) is now rejected with a 400 instead of either being stored broken or crashing to a 500. Sign-off given; see item 2 below for what specifically was broken. Verified: 48/48 tests pass (10 new).
- [x] **Custom exceptions + centralized error handling** — done as part of the robustness pass below, once the response-shape question was settled (see item 3). New `exceptions.py`; `app.py` registers the handlers.
- [x] **`app_logginig/` package typo** — flattened `app_logginig/logger.py` (a directory for one file, smaller than either `extensions.py` or `exceptions.py`) into a single top-level `app_logging.py`, fixing the typo at the same time. `config.py`/`extensions.py`/`exceptions.py` stay flat at the root too, deliberately not grouped into a `core/`-style package - none of these are big or numerous enough yet to justify the import-path indirection; revisit if the root's flat infrastructure files grow past 7-8.
- Cosmetic, optional, not scheduled: `views/` are really route/blueprint modules, not "views" in the Django sense.

## 1. Scalability

- [x] `GET /api/recipes` is now paginated — `?page=`/`?pageSize=` (default 20, capped at 100 server-side), applied via `.offset()/.limit()`. Response body stays a bare JSON array (no contract break); pagination metadata (`total`/`page`/`pageSize`) is exposed via `X-Total-Count`/`X-Page`/`X-Page-Size` response headers instead, so `recipes-ui` keeps working unmodified and only sees the first page until it's updated to read the headers. Verified live: the same endpoint that returned a 699KB body against the dev DB's 502 accumulated recipes now returns 18KB for the default page.
- [x] N+1 queries in `Recipe.to_dict()` fixed alongside pagination — `selectinload` on `Recipe.author` and `Recipe.parts` → `RecipePart.ingredients`, so a page of recipes costs a small fixed number of queries instead of `1 + N + N + (N × parts)`.
- [ ] Gunicorn `--workers 2 --threads 2` is hardcoded in both the Dockerfile `CMD` and `run_app.sh` — make it env-driven.

## 2. Security

- [x] `SECRET_KEY` and `JWT_SECRET_KEY` were the same value (`app.py`) — now loaded as two independent required env vars in `config.py`. Turned out the production Kubernetes secret (`recipes-cluster-resources/platform/external-secrets/recipes-external-secret.yaml`) already provisions both separately — the app just never read the second one. Verified: app boots fine with both set, all 37 tests pass.
- [x] No rate limiting on `/api/users/login` or `/register` — added `flask-limiter` (`extensions.py`), `10 per minute` on login, `5 per hour` on register, disabled under `TESTING` so the suite isn't throttled. Verified live: 15 rapid login attempts through docker-compose returned `401` ×10 then `429` ×5, exactly at the configured limit. **Known limitation**: in-memory storage, correct for today's single-replica deployment but per-pod if ever scaled — noted in code.
  - [x] Also disabled under `FLASK_ENV=development` (`app.py`, same flag as `TESTING`) — a developer manually exercising `/register`/`/login` against a local docker-compose stack (re-submitting a form, retrying after a 409) hit the same 5/hour register limit meant for real traffic, with no way to reset it short of restarting the container. Still fully enforced in staging/production. Verified live: 7 consecutive register requests all returned their normal status (`400` for an incomplete body) instead of `429` after the 5th.
- [x] No `MAX_CONTENT_LENGTH` on the Flask app; recipe creation accepted unbounded nested `parts`/`ingredients` arrays. Added `MAX_CONTENT_LENGTH = 1MB` (413 before the route runs) plus explicit caps of 50 parts/recipe and 50 ingredients/part (400, checked before any DB mutation). Verified live: a 2MB body → `413`; 51 parts → `400`.
- [x] Every direct dependency in `requirements.txt` is now pinned to an exact version (`Flask==3.1.3`, `Flask-SQLAlchemy==3.1.1`, `Flask-Bcrypt==1.0.1`, `Flask-CORS==6.0.5`, `psycopg2-binary==2.9.12`, `PyJWT==2.13.0`, `flask-jwt-extended==4.7.4`, `Flask-Limiter==4.1.1`, plus the two already-pinned). Versions were the ones verified working via the docker-compose build + full test suite. **Residual gap**: this pins direct dependencies only — transitive dependencies (`sqlalchemy`, `werkzeug`, `bcrypt`, `click`, ...) still resolve freshly on every build. A real lockfile (`pip-compile`/`uv`/`poetry`) would close that, but is a bigger tooling change (new build step, Dockerfile change) — worth a deliberate follow-up, not bundled into this pass.
- [ ] Builder stage installs `gcc`/`libpq-dev` to build wheels, but `psycopg2-binary` already ships prebuilt. **Not actually a security fix** — worth being honest about: multi-stage build already excludes the builder's packages from the final image, so there's zero attack-surface impact on what ships. It's a build-time efficiency nit (slower CI builds, nothing more) — leaving it out of this security pass; can revisit as general Dockerfile cleanup.

## 3. Robustness

- [x] Inconsistent error-response shape across the API — `user_controller` used `{"message": ...}`, `recipe_controller` used `{"error": ...}`. Unified: every error response now carries both keys with identical text (`{"error": "...", "message": "..."}`), so no existing consumer of either key breaks. New `exceptions.py` (`ApiError` + `BadRequestError`/`UnauthorizedError`/`ForbiddenError`/`NotFoundError`/`ConflictError`) and two handlers registered once in `app.py` (`register_error_handlers`) are what actually shape every response now.
- [x] `recipe_views.get_recipes` no longer catches anything locally — the try/except that used to mask a real crash as `[]`, `200` is gone; any failure now flows to the same centralized handlers as everything else.
- [x] The duplicated `try/except → rollback → log → return (dict, status)` block is gone from every controller method in both `user_controller.py` and `recipe_controller.py` — controllers `raise` a typed exception (or just let a DB exception propagate) instead of hand-building a response tuple and remembering to roll back. Structured logging context (`action`/`status`/entity ids) is preserved via `extra_props` on the exception, forwarded to the log call the handler makes.
- [x] Inconsistent ORM access style: the two remaining `Model.query.get(id)` call sites (`recipe_controller.get_recipe_by_id`, `user_controller.get_author_by_id`) switched to `db.session.get(Model, id)`, matching every other lookup in both files.
- [x] Added `SQLALCHEMY_ENGINE_OPTIONS` (`pool_pre_ping=True`, `pool_recycle=1800`) so a stale pooled connection (DB restart/failover) is transparently detected and replaced instead of surfacing as a random request failure.
- [x] `run_app.sh` was broken (`gunicorn app:app`, but `app.py` never defines a module-level `app`) — fixed as part of the `config.py`/`extensions.py` pass since it touched the same startup path.
- [x] Dockerfile builder stage installed `gcc`/`libpq-dev` for no reason — every dependency ships a prebuilt wheel. Removed; image still builds and runs correctly.
- [x] `system_views.py`'s `/health`/`/ready`/`/startup` gave an opaque single-status-string response and never logged anything, even on failure — meaningful during an actual outage only if you already knew where to look. `/ready` and `/startup` now return a `checks: {"database": "ok"|"unreachable"}` object (extensible if another dependency is ever added) and log a warning with the real exception server-side on failure; `/health` now includes `version` (`APP_VERSION`, now centralized in `config.py`). Categorical status only, never the raw exception, in the response body — worth noting these three endpoints are publicly reachable (the Ingress uses a catch-all `path: /`), which is exactly why the real error stays server-side.
- [x] `GET /api/recipes/<id>` was dead code — `RecipeController.get_recipe_by_id` existed and was fully implemented, but no route in `recipe_views.py` ever called it, so single-recipe lookups were unreachable. Wired up as a public (no-auth, matching `GET /api/recipes`) route.
- [x] Recipe create/update accepted malformed input that either violated a DB `NOT NULL` constraint (missing `title`, nameless ingredients) or crashed the view outright (`"parts": null`, iterated as `None`) — both surfaced as an opaque 500 to the client instead of a clean 400. Closed by the new validation layer (see item 4) plus two targeted fixes in `recipe_controller.py`: `parts_data = data.get('parts') or []` (was `.get('parts', [])`, which doesn't catch an explicit `null`) on create, and an explicit `is not None` guard before rebuilding `recipe.parts` on update. Also fixed: ingredient `amount`/`unit` had no fallback on update (`ing_data.get('amount')`) while create did (`ing_data.get('amount', 0)`) — an omitted `amount`/`unit` on update would hit the same `NOT NULL` constraint; both paths now default consistently.

All of the above verified: 48/48 tests pass (38 from the prior pass + 10 new covering the single-recipe route and the validation/crash fixes), and live through the full docker-compose stack — a login failure and a recipe 404 both now return `{"error": "...", "message": "..."}` with matching text; an oversized request hits my Flask-level 413 handler directly (JSON body) independent of nginx's own body-size cap in front of it.

---

**Order of attack:** restructuring (this doc) → pin dependencies → fix pagination/N+1 (same fix) → centralize error handling (fixes response-shape inconsistency + the silent-failure bug together) → rate limiting + request size limits → validation layer.
